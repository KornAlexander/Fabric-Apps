# Power BI report window in an app

Click something in your app, and its Power BI report opens right there, filtered to what you
clicked: a building, a station, a customer. This skill is the method for building that into a
Fabric App, written so that a coding agent can follow it and a person can read it as a checklist.

```
click an object  ->  "Report"  ->  floating window inside the app
                                    iframe: app.powerbi.com/reportEmbed
                                    one report page, filtered to that object
```

## How to use it

| You want to | Do this |
|---|---|
| Let a coding agent build it | Point the agent at this file, or copy the `pbi-embed` folder into your project's skills folder (`.agents/skills/` or `.claude/skills/`), and ask for a Power BI report window. |
| Build it yourself | Work through sections 1 to 9 in order. Section 1 is the decisions, section 9 is the checks. |
| See it working first | The worked example is this app. Start with the runbook, then the two files that hold the whole embed. |

**The worked example, in this folder:**

- [docs/POWER-BI-EMBED.md](../../../docs/POWER-BI-EMBED.md): the runbook, with what was measured, the exact commands and a table of everything that went wrong once.
- [src/powerbi/embedUrl.ts](../../../src/powerbi/embedUrl.ts): the embed address, as one pure function.
- [src/config/powerbi.ts](../../../src/config/powerbi.ts): which site and language open which report, and the gate that decides whether the button is offered.
- [src/powerbi/BuildingReportWindow.tsx](../../../src/powerbi/BuildingReportWindow.tsx): the window.
- [tools/fabric/](../../../tools/fabric/): lakehouse load, semantic model, generated report and publishing, as scripts.

## What to expect

| | |
|---|---|
| App registration, tokens in the app | None. Power BI signs the viewer in itself. |
| Sign-in | One click on Power BI's own button on first use per browser. Measured in Chrome and Edge, inside the Fabric portal. |
| Changing the object | The report page reloads, about 4 to 6 seconds. |
| Languages | A second report over the same model per language; number formats follow the app. |
| Security | The URL filter selects, it does not protect. Restricting data needs row-level security. |
| Not measured | A viewer who is not an admin, blocked third-party cookies, sign-in after a browser restart, and the JavaScript SDK variant. |

## 1. Decide before building

| Fork | Recommended | Alternatives |
|---|---|---|
| Embedding method | Secure embed iframe: `https://app.powerbi.com/reportEmbed?reportId=…&autoAuth=true&ctid=…` | JS SDK with a user token (needs an Entra app registration); app-owns-data (service principal and a backend endpoint) |
| Trigger | A button for the open object, in its panel AND on the main view | Open on click; a separate mode |
| Window | Floating, follows the open object and closes with it | Modal; docked pane; pinned window |
| Report | A new compact page built for the window (1280 x 720), generated by a script | An existing report; a full-size template page |
| Sites | One lakehouse, model and report per site | One shared model with a site column (only with row-level security) |
| Languages | A second report per language over the same model, picked by the app's language | One report with mixed language; a second model per language |
| Ids | Wherever the deployer wants them; ask | Untracked env file; shell variables |

What the SDK would change: filter changes without a reload, and real loaded and error events. What
it does to sign-in was NOT measured in this app. The PBI Fixer app in this repository implements the
SDK method and is the place to start if you need it:
[LiveReportPreview.tsx](../../../../../../fabric-admin/pbi-fixer/src/components/explorer/LiveReportPreview.tsx)
and [fabricAuth.ts](../../../../../../fabric-admin/pbi-fixer/src/services/fabricAuth.ts).

## 2. Spike first, in the real nesting

The risky part is sign-in inside nested frames, and it cannot be tested on localhost. In the Fabric
portal the chain is portal, then a sandboxed frame, then the app on its hosting address, then
Power BI.

1. Publish a throwaway two-page report on the model.
2. Open the embed address directly in a signed-in browser. Read the page text to check `pageName`,
   the filter and the numbers against a DAX query.
3. Load the same address in an iframe inside the deployed app, inside the portal. URL parameters do
   not pass through the portal, so give the spike a hidden way in that does not need them.
4. Record: does it render, is there a sign-in prompt, does it persist, how long a filter change
   takes. Measured here: one sign-in click on first use per browser profile; a filter change is a
   full reload of 4 to 6 seconds. A browser profile that keeps no session between starts asks again
   after every start, so test the restart case in the browser your viewers really use.
5. Delete the spike report and the hidden entry afterwards.

A minimised browser window makes screenshots hang. Restore it first. A browser automation tool that
can enter cross-origin frames reads the report's text directly, which is better evidence than a
picture taken while the visuals are still painting. The app's direct hosting address asks for its
own sign-in; test inside the portal instead.

## 3. The embed address

```text
https://app.powerbi.com/reportEmbed
  ?reportId=<report id>
  &autoAuth=true
  &ctid=<tenant id>
  &pageName=<page name>
  &filter=Building/building_code eq '5606'
  &filterPaneEnabled=false&navContentPaneEnabled=false
  &language=en&formatLocale=en-GB
```

One line in practice; broken up here to be readable. The rules behind each part:

- Always quote the value: `Table/column eq '5606'`. An unquoted numeric-looking code compares a
  number with a text column and matches nothing.
- Table and column names with spaces or special characters are escaped as `_xHHHH_`
  (`Room Hour` becomes `Room_x0020_Hour`), not URL-encoded.
- Double a single quote inside a value. Build the query string with `encodeURIComponent`, not
  `URLSearchParams`, which turns spaces into `+`.
- `pageName` is the page's internal name (the folder name in PBIR), not its display name.
- Both `filter` and `$filter` work on `reportEmbed`.
- `filterPaneEnabled=false&navContentPaneEnabled=false` for a small window.
- `language=en&formatLocale=en-GB` sets Power BI's own texts and the number format. Send both or
  neither, and validate them as tags. They do not translate the report.
- Validate both ids as GUIDs and return nothing otherwise, so a bad value cannot rewrite the
  address and a missing one ends in no button.
- Pass the code exactly as the app holds it. Never change its letter case on the way.
- The filter is not a permission. Restricting data needs row-level security.

## 4. Make the report say what it shows

- Put a measure in the page title that names the filtered object and tells three cases apart: one
  object, a filter that matches nothing, and no filter at all. A filter that did not apply
  otherwise looks like a correct page.
- Stamp the data load in a one-row table (real or synthetic, period, load time, one hash over ALL
  source files, not only the main one), show it on the page, and check before deploy that
  1. the model is the load of the files on disk,
  2. that data state agrees with what the app shows, in both directions,
  3. the server the DEPLOYED app reads its data from serves those same files.
- Keep the stamp line under about 100 characters, or it is cut off on the page.
- Give the title box room for a descender. A box that fits "Gebäude" cuts the "g" of "Building".
- Decide per measure what "unknown" looks like. Blank where nothing is known, zero only where
  zero is known. `COUNTROWS` over nothing is blank, so a known zero needs
  `IF([total] > 0, COALESCE([count], 0))`.
- A heatmap needs a measure that divides by the hours in the filter, not by the whole period.
- Colour by a measure with fixed steps rather than a min-max gradient, so the same colour means
  the same thing for every object, and unknown gets its own colour off the scale.
- Give weekday and similar text columns a sort column.
- Set table and matrix column widths; auto-size hands a long name column everything.

## 5. More than one site

- One site, one lakehouse, one model, one report. Do not put sites into one model as a column:
  a URL filter is not a permission, and Direct Lake viewers need access to the data, so data that
  may be shown to anyone must not share an item with data that may not.
- Keep what differs between sites in one profile (names of the items, source folder, which release
  lever governs the data, the data state when the source does not say). Never leave a per-site
  number as a constant: the teaching week was 70 hours at one site and 60 at the next, and the
  wrong one silently makes every utilisation about 14 % too low.
- Item ids come from the shell, and the shell remembers the last site. Before writing, ask the
  service for the NAME of the item behind the id and refuse when it is another site's. Make that
  check mandatory, not an optional flag.
- Look at the keys before loading. If two codes differ only by letter case, the model needs a
  case-sensitive collation (`collation: Latin1_General_100_BIN2_UTF8` in `model.tmdl`), and that
  can only be set when the model is created. Without it every query fails on duplicate keys, and
  a filter on one code would match both. With it, the URL filter is exact.
- To check a model's case sensitivity, do NOT compare two literals: `"a" = "A"` is true in every
  model. Count distinct values instead:
  `COUNTROWS(DISTINCT(UNION(ROW("x", "a"), ROW("x", "A"))))` is 1 without the collation, 2 with it.
- Model descriptions are claims that Copilot and tooltips repeat. Reword them per site so a
  generated site never says its codes are a real institution's, and make the generator refuse a
  generated site whose descriptions still name real sources.

## 6. More than one language

- A second language is a second report over the SAME model, with the same page name and the same
  filter column. Every number is the same measure under another header (`displayName`), so the two
  pages cannot disagree.
- Only what a report cannot rename exists twice: measures that answer in words (the title, the
  stamp), and label columns of the stamp. Add them only for a site that has the second report, and
  reload the lakehouse before publishing the model that names the new columns.
- Decide what happens to data values (usage types, names). Showing them as the app shows them keeps
  window and panel identical.
- A site without a report in the reader's language opens its own report. A second-language id that
  is missing or malformed is "not configured": it falls back the same way and never removes the
  button.
- Refuse to generate or publish a language the site has no report in. Falling back to the main
  language there would publish over the main report under its name.
- Test that both languages read the same measures, that no word of the first language is left on
  the second page, and that every measure a page reads exists in the generated model.

## 7. Publish reproducibly

- Generate the PBIR folder from a script. Give visuals ASCII names and deterministic page names.
- Publish through the Fabric REST API (`POST /v1/workspaces/{ws}/reports`, then
  `updateDefinition` for the same display name so the id is kept). Write `definition.pbir` at
  publish time as `byConnection` with `semanticmodelid=<id>`; that short form is accepted.
- Refuse to update a report of the same name that reads from another model, and refuse when the
  binding cannot be read.
- Follow the long-running operation to its end. After adding a table to a lakehouse, a Direct Lake
  reframe can fail for about two minutes until the table is registered: read the result back and
  retry. Accept only a refresh entry that did not exist before the request; the newest entry can
  still be the previous, completed one.
- `az account get-access-token --tenant <tenant>`: `az` drifts to the home tenant.
- Never keep tokens or print them.

## 8. In the app

- A pure function builds the address; a pure gate decides whether the button is offered. Every
  unknown is "no": no report for the site, site not shipped, malformed ids, data posture differs.
  State what a report is made of on the report's own config entry; do not derive it from site
  data that a release switch may strip.
- Hold the window's open state where it survives panel changes, derive the address from the open
  object each render, and key the iframe on the address so each object gets a fresh frame.
- Offer a second button on the main view: a button that lives only in a panel disappears when
  another panel takes its place while the object stays open.
- A deep link flag (`report=1`) is honoured only with an object that exists, is written back as
  the window opens and closes, and is dropped on every switch to another site.
- Remember the window's size and place in local storage, but write only after the viewer moved
  it, so a small screen's clamp does not overwrite the place chosen on a large one.
- Open the window below the main view's top controls, so it does not cover its own button.
- The app cannot see into the frame: `onLoad` fires for sign-in and error pages too. Show a
  first-use hint and an "open in new tab" link instead of a loaded state.
- While dragging the window, stop the content from taking pointer events; an iframe swallows them.
- Move focus into the window on open and back on close; close on Escape only when the focus is
  inside it. Keep menus above the window in the stacking order.
- Load the window lazily, inside an error boundary that says "reload the page": after a deploy an
  open tab asks for a chunk that no longer exists, and without the boundary the whole app goes.
- Vite inlines the whole environment object into the bundle when any code reads
  `import.meta.env[name]` dynamically, so every `VITE_*` value is in every bundle.

## 9. Check

- Unit tests for the address builder and the gate, with a mirror test that the report IS offered
  where it should be, and sabotage each rule once to see a test fail. Run them in every release
  posture the project has.
- A browser test that blocks `app.powerbi.com` and asserts only the frame's `src`, with made-up
  ids in the dev server's environment. Build those ids from parts, so no file holds a whole id that
  a publish gate would have to take for a tenant's. If the test may skip for a server without them,
  let it ask the server which ids it serves instead of guessing from environment variables.
- A build check on the bundle: treat every report id found as the governed one unless it
  demonstrably belongs to an ungoverned site, treat a configured governed id as governed in
  whatever slot it stands, and say so when there is no build to check. Test that rule on crafted
  bundles; the bundle of the day rarely exercises the direction that matters.
- A model check that compares the app's own figures with DAX, including one object found in the
  data that must show a known zero.
- After deploy, look signed in, inside the portal, in every language, and compare one number with
  the app.
- List what was not tested (other browsers, a viewer who is not an admin, blocked third-party
  cookies, sign-in after a browser restart) and hand the owner a checklist with the expected
  numbers.

## Boundaries

Publishing a report, loading a lakehouse, creating a lakehouse or model, deploying an app,
creating an app registration, sharing items and deleting items each need the owner's go for the
exact target. Sign-in is the owner's: click an ordinary sign-in button, never enter credentials or
codes.
