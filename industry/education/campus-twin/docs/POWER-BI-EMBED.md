# Power BI report window

A building in the 3D twin can open a Power BI report page in a small floating window, filtered to
that building. This document is the process that produced it, written so it can be repeated for
another site or another app. Every command below was run on 2026-10-10, for two sites.

```
click a building  ->  building panel  ->  "Bericht"  ->  floating window
                                                          iframe: app.powerbi.com/reportEmbed
                                                          page "gebaeude", filter Building/building_code
```

Two sites have a report:

| Site | Data | Offered when |
|---|---|---|
| TUM Garching (`garching`) | Real TUMonline bookings | The release switch ships the real TUM data (`navigatumData: "include"`) |
| Beispiel-Universität (`campus-demo`) | Generated: invented institution, rooms and week | Always. Nothing in it is anybody's real data |

Beispiel-Universität has its report twice, in German and in English. The window opens the one that
matches the app's language; see "Languages" below.

## How a viewer reaches it

- **In the building panel:** "Bericht" next to the building's name, in the occupancy lens.
- **On the scene:** a button beside the compass, "Bericht Gebäude <code>", for as long as a building
  with a report is open. It is there because the panel is not always: another lens or the assistant
  can take its place while the building stays open. Both buttons are one switch.
- **By link:** `?aoi=<site>&building=<code>&report=1` opens the building and its report. The flag is
  honoured only together with a building that exists, and the address bar gains and loses it as the
  window opens and closes, so the address is always a link to what is on screen.

The window reopens where it was last left and at the size it was given, per browser (local
storage, key `campus.reportWindow`). A remembered place is clamped to the current screen.

## What was decided, and why

| Decision | Choice | Reason |
|---|---|---|
| Embedding method | Secure embed iframe (`reportEmbed`, `autoAuth=true`) | No app registration, no secret, no token handling. Power BI signs the viewer in and decides what they may see. |
| Trigger | A "Bericht" button for the open building, in its panel and on the scene | The click on a building keeps its meaning (open the building). Sites without a report simply have no button. |
| Window | Floating, draggable, resizable; follows the open building and closes with it | The window and the scene can never name two different buildings. |
| Report | One compact page, 1280 x 720, generated by a script | A full 1920 x 1080 page scaled into a 720 px window is unreadable. Generated so it cannot drift from the model. |
| Data state | Stamped in the lakehouse, shown on the page, checked before deploy | The tables look the same for real and synthetic bookings. Only a stamp can tell a report which it is showing. |
| One site per model | Each site has its own lakehouse, model and report | A URL filter is not a permission, and Direct Lake viewers need access to the data. Data that may be shown to anyone must not share an item with data that may not. |
| Configuration | Report ids and tenant id in `.env.production`; page name and filter column in code | Ids belong to one tenant. The page name and the column are an interface with the report generator. |

### What the spike measured

Tested in Chrome with the workspace owner's account, nested as Fabric portal, then app, then
Power BI:

- The report renders inside the app inside the portal.
- The first open in a browser profile shows Power BI's own "sign in" button. One click completes
  single sign-on without asking for credentials. After that it stays signed in, also across reloads.
  Silent sign-in does not happen on first use, because Power BI is a third party inside the frame.
- `pageName` selects the page. Both `filter` and `$filter` apply the filter.
- A building change is a full reload of the frame, about 4 to 6 seconds.
- An unknown building shows blank values, not zeros. A building with rooms and no teaching room
  shows 0 teaching rooms: that count is known.
- The app cannot tell whether the embed worked: a cross-origin frame reports "loaded" for the
  sign-in page and for an error page too. Hence the "open in new tab" link in the window footer.

### Not tested yet

Run these before relying on the window for an audience that is not you:

- [ ] A viewer who is not workspace admin, with exactly the access you intend to grant. The models
      are Direct Lake, so the viewer needs access to the report, the model and the lakehouse.
- [ ] A browser profile that blocks third-party cookies.
- [ ] Whether the sign-in survives a restart of an everyday browser. A profile that keeps no session
      between starts asked again after every start (Edge, 2026-10-12).

### The upgrade path that was not taken

The Power BI JavaScript SDK (`powerbi-client`) with a user token changes two things: the building
filter can be changed without reloading the report, and the app receives loaded, rendered and error
events. It needs an Entra app registration with delegated `Report.Read.All` and a redirect for the
hosting address.

**It was not built here, and what it does to sign-in was not measured.** With the SDK the app hands
Power BI a token instead of Power BI signing the viewer in inside the frame. Whether the viewer then
still has to click once, and where (in the frame, or in a sign-in window the app opens for the
token), has to be measured inside the Fabric portal before anyone relies on it.

The PBI Fixer app in the Fabric-Apps repository implements this method and is the place to start:
`fabric-admin/pbi-fixer/src/components/explorer/LiveReportPreview.tsx` embeds with the SDK, and
`src/services/fabricAuth.ts` beside it gets the token (a sign-in window on first use, started from a
button, and silent afterwards, by its code).

`src/powerbi/embedUrl.ts` is the only place that knows the address format, and
`BuildingReportWindow.tsx` is the only place that renders the frame, so the switch is contained in
those two files.
## Languages

The app speaks German and English, and the window follows it in two independent ways.

| What | How | Where |
|---|---|---|
| Number and date format, and Power BI's own texts | `language` and `formatLocale` on the embed address, for every site | `embedUrl.ts` |
| The report's own words (titles, headers, footnote, title and stamp) | A second report in that language, where the site has one | `variants` in `src/config/powerbi.ts` |

A second language is a second report over the **same model**, with the same page name and the same
filter column. Every number on both pages is the same measure under another header. Only the two
measures that answer in words exist twice (`Gebäude im Filter` / `Building in filter`, `Datenstand` /
`Data status`), and the load stamp has its labels in both languages. Data values, such as usage
types, are shown as the app shows them, in both languages.

A site without a report in the reader's language opens its own report: Garching has a German report
only, and an English reader gets that one with English number formats. A second-language id that is
missing or malformed counts as "not configured" and falls back the same way; it never removes the
button.

Measured on 2026-10-12 with the demo report, opened directly: `language=en&formatLocale=en-GB` shows
1,165 rooms, `language=de&formatLocale=de-DE` shows 1.165, for the same viewer.

The same day inside the Fabric portal, in Edge with a profile that had never opened Power BI in a
frame: the English app opened the English report (1,165 rooms, 43.9 % for building H), the German
app the German one (1.165, 43,9 %). Power BI asked for its one sign-in click on the first open and
not again for the second building or the other language.

To give a site an English report: add `english=English(...)` to it in `tools/fabric/sites.py`, then
run steps 1 to 4 again for that site (the load writes the English stamp labels, the model gains the
two English measures) and step 4 once more with `--lang en`. Reload before publishing the model: the
model then names stamp columns the old table does not have.

## The filter is not a permission

A URL filter narrows what the page shows. Anyone who can open the report can remove it and see every
building in that model. If a viewer must only see some buildings, that is row-level security in the
semantic model, not this feature. It is also why sites do not share a model.

## Prerequisites

- `az login`, and the tenant the workspace lives in. `az` drifts to the home tenant, so the scripts
  take the tenant explicitly.
- Contributor on the workspace (to publish), and the capacity running.
- A Python with `pyarrow` and `deltalake` for the lakehouse step. The other scripts need only the
  standard library.
- A tenant that allows embedding Power BI content. Check the Fabric admin setting if the frame
  refuses to load at all.

```powershell
$env:FABRIC_TENANT_ID         = "<tenant guid>"
$env:FABRIC_WORKSPACE_ID      = "<workspace guid>"
$env:FABRIC_FOLDER_ID         = "<folder guid>"           # optional, used when an item is created
$env:PYTHONIOENCODING         = "utf-8"
# per site, and they differ between sites:
$env:FABRIC_LAKEHOUSE_ID      = "<that site's lakehouse guid>"         # printed by step 0
$env:FABRIC_SEMANTIC_MODEL_ID = "<that site's semantic model guid>"    # printed by step 2
```

`az rest --url https://api.fabric.microsoft.com/v1/workspaces/<id>/items` lists the ids.

Every script takes `--site garching` or `--site campus-demo` (default `garching`). The two ids
above come from the shell, and the shell that worked on one site still holds that site's ids. The
scripts that write therefore ask Fabric for the NAME of the item behind the id and refuse when it is
another site's. Both refusals were tested by pointing the demo site at Garching's items.

## The steps

Shown for `<site>`; leave `--site` out for Garching.

### 0. The lakehouse

```powershell
python tools/fabric/setup_lakehouse.py --site <site>
```

Creates the site's lakehouse, or finds it, and prints its id.

### 1. Load the lakehouse, with its stamp

```powershell
python tools/fabric/build_lakehouse_tables.py --site <site>
```

Writes the six tables and `data_load`, one row that says what the load is: real or synthetic,
which semester, one hash over the rooms file and the bookings file (`rooms.json` and
`occupancy.bin`), and when. For a site a release lever governs, the loader refuses when the rooms
file and `config/release.json` disagree: real bookings need `navigatumData: "include"`, and under
`include` a synthetic rooms file is refused too, because the app would show the real week beside it.

### 2. Publish the model

```powershell
python tools/fabric/build_semantic_model.py --site <site>
```

Generates the TMDL, creates or updates the model and reframes it. `--write-only` stops after
writing the TMDL to `fabric/`. A table that is new to the lakehouse can take about two minutes to be
registered; the script reads the reframe result back and retries instead of reporting success on a
request. The teaching week (70 hours at Garching, 60 at the demo site) is read from the rooms file.
For a site that needs a case-sensitive model it then asks the model whether it tells `a` from `A`,
and stops if it does not: a collation sent to a model that already exists changes nothing.

### 3. Prove the model and the app agree

```powershell
python tools/fabric/verify_model_agreement.py --site <site>
```

Compares thirteen figures computed from the app's own assets with the same figures from DAX
(twelve where the site has no building without a teaching room), and
checks the stamp: the model must be a load of this site, of the files on disk, allowed under the
current release posture, and the map server the deployed app reads from (`VITE_TERRAIN_BASE`) must
serve those same files. The last one matters because `public/terrain/` is not in git and is
published separately: without it the model can match this disk while the running app shows an
older build. Do not continue on a failure.

### 4. Generate and publish the report

```powershell
python tools/fabric/build_report.py --site <site> --theme "<path to a Power BI theme json>"   # --theme is optional
python tools/fabric/publish_report.py --site <site>
```

For a site with an English report, both again with `--lang en`: it writes `<artefact>EN.Report` and
publishes it under the site's English report name, bound to the same model.

The first writes the PBIR folder, the second sends it and prints the report id. Publishing again
updates the same report and keeps its id. It refuses when the model id in the shell is another
site's model, and when a report of the same name reads from a different model. Without `--site` it
needs `--source`, `--name` and `--model-name`, and it will not publish without knowing which model
to expect.

Open the report once in the service, with and without a filter, before trusting it. A successful
import does not prove the visuals render.

```
https://app.powerbi.com/reportEmbed?reportId=<report id>&autoAuth=true&ctid=<tenant id>&pageName=gebaeude&filter=Building/building_code eq '<code>'
```

The page title must name the building. "Alle Gebäude (kein Gebäudefilter aktiv)" means the filter
did not apply; "Gebäude nicht im Datenbestand" means it applied and matched nothing.

### 5. Tell the app

In `.env.production`:

```
VITE_PBI_TENANT_ID=<tenant guid>
VITE_PBI_REPORT_GARCHING=<Garching's report id>
VITE_PBI_REPORT_DEMO=<the demo site's report id>
VITE_PBI_REPORT_DEMO_EN=<the demo site's English report id>
```

The page name and the filter column are in `SITE_REPORTS` in `src/config/powerbi.ts` and must match
`PAGE` and the filter column in `tools/fabric/build_report.py`.

`.env.production` is your deployment's own file; this template does not ship one and `.gitignore`
keeps it out of commits. The ids are not
secrets, but they are one tenant's coordinates: if your copy of the repository is public, run
`python tools/verify_publishable.py` and read what it says about them before you push.

### 6. Test

```powershell
npx tsc -b
npx vitest run
$env:CS_E2E_PORT = "4188"; npx playwright test e2e/building-report.spec.ts --project=chromium
npx vite build
node tools/check_release.mjs
```

`check_release.mjs` fails when the built bundle lacks Garching's configured report id while the real
data ships (a stale `dist/`), and when it carries one while the data is withheld.

### 7. Deploy and look

```powershell
node tools/deploy.mjs
```

Then, signed in, inside Fabric: open a building on each site, press "Bericht", and compare the KPI
row with the building panel. The teaching-room utilisation in the window and in the panel are the
same measure and must show the same number.

## Where the button appears

`gateReport` in `src/config/powerbi.ts` decides, and every unknown is a no:

1. the site has an entry in `SITE_REPORTS`;
2. the build ships the site;
3. report id and tenant id are well-formed;
4. a report marked `realData: 'navigatum'` is offered only while the release switch is exactly
   `include`. It is loaded from real bookings and says so; beside a synthetic week it would be a
   second, different answer about the same room. A report without that mark (the demo site) is not
   governed by the switch.

## Adding a report for another site

1. Add the site to `SITES` in `tools/fabric/sites.py`: its AOI, the names of its three items, the
   release lever that governs it (or none), and what its data state is when the rooms file does not
   say.
2. Look at its building and room codes before loading. If two differ only by letter case, give the
   site a case-sensitive `collation`; Power BI ignores case otherwise, and the collation can only be
   set when the model is created.
3. Check that the building code the 3D scene emits is the value in the filter column. For both
   sites here they come from the same `rooms.json`, so they are identical by construction.
4. If the site's descriptions would make a claim that is not true for it, extend `wording()` in
   `build_semantic_model.py`. The generator refuses a generated site whose descriptions still name
   TUM's systems.
5. Run steps 0 to 4 with `--site <site>`.
6. Add the site to `SITE_REPORTS` with its own `VITE_PBI_REPORT_<SITE>` variable, and mark it
   `realData` if a release lever governs its data.
7. Add the site to `e2e/building-report.spec.ts` and a sentinel id to `playwright.config.ts`.

## Things that went wrong once

| Symptom | Cause | Where it is handled |
|---|---|---|
| Report window shows a sign-in button inside the app | First use in this browser profile; Power BI is a third party in the frame | Expected. The window footer says so. |
| Model refresh fails with "source tables either do not exist" right after a load | A new Delta table is not registered in the lakehouse yet | `reframe()` in `build_semantic_model.py` retries |
| Every query fails with "contains a duplicate value" on a key column, although the codes are distinct | Two codes differ only by letter case (`AA`, `aa`) and the model ignores case | `collation` in `sites.py`, set at model creation |
| A filter on one building shows two buildings added together | The same: the filter compares without regard to case | The same collation |
| One site's data ends up in another site's lakehouse or model | The item ids come from the shell, and the shell remembers the last site | `expect_lakehouse` and `--model-name` compare names before writing |
| Utilisation about 14 % too low on a second site | The teaching week was a constant, 70 hours | Read from the rooms file per site |
| Import fails with "Property 'name' has unsupported characters" | A visual's `name` (its id) is not ASCII | `publish_report.py` refuses before sending |
| Weekdays in alphabetical order | No sort column on the weekday name | `SORT_BY` in `build_semantic_model.py` |
| A filtered page shows campus totals | The filter did not apply | The page title is the measure `Gebäude im Filter` and says so |
| Filter on a table with a space in its name is ignored | The name must be escaped as `_x0020_`, not URL-encoded | `odataName` in `embedUrl.ts` |
| Numeric-looking code matches nothing | `eq 5606` compares a number with a text column | `filterExpression` always quotes |
| Heatmap cells all near 1 % | A whole-week utilisation measure used inside one hour | `Belegung im Zeitfenster %` divides by the hours in the filter |
| A tile shows "(Leer)" for a count that is known to be zero | COUNTROWS over nothing is blank, the glyph the page uses for "unknown" | `Lehrräume im Filter`: zero where the filter holds rooms, blank where it holds none |
| A probe for case sensitivity says "insensitive" on a model that is not | Two literals compared with `=` ignore case in every model | `require_collation` counts the distinct values of {"a", "A"} instead |
| The stamp line on the page is cut off | The line holds about 100 characters | `source_labels` and `semester_label` in `sites.py` are kept short |
| Screenshots of the embedded report hang during automated checks | The browser window was minimised | Restore the window first |
| The window writes 1.165 where the panel beside it writes 1,165 | The format followed the viewer's Power BI settings, not the app | `locale` in `embedUrl.ts` sends the app's language |
| Model refresh fails after a site gained an English report | The model names the English stamp columns before the lakehouse was reloaded | Load first (step 1), then the model (step 2) |
